## Acceptance Criteria
AC1 Spacing: automatic goal continuations are at least 30 s apart. With a low-activity streak n (consecutive continuations with no observed state change), the delay is min(30 s * 2^(n-1), 30 min). Any observed state change resets the streak to the floor. Fake-time unit tests cover n=1,2,3, the cap, and the reset. AC2 Two read-only polls GROW the streak (they do not evade it), measured end to end: an app-server integration test with two consecutive poll-only continuations asserts the request count and the second delay (plan section 11 attack 'two read-only polls evade the streak'). AC3 Exactly one live timer per goal thread: a new schedule cancels and replaces the old one, no detached sleeps accumulate, and an event wake (mail, child completion, subscribed exec notification) pre-empts the timer (tests). AC4 A ticket binds goal identity and revision, the predecessor turn, and the generation/cause. It is invalidated by human input or steering, goal change or clear, stop, completion or release, and any new turn. A user turn that starts AND ends before the old deadline still invalidates it (fast intervening human turn test). Admission rechecks the ticket together with predecessor and pending-mail state; a stale ticket never starts a turn (narrowing mutant: skip the revision or generation check). AC5 The three-fully-empty-continuations blocker runs FIRST and is unchanged. A nonempty 'waiting' continuation is paced, not classified as empty (test). AC6 Timers and counters are transient: resume reconciles the goal and restarts at the floor, never restoring stale subscriptions or streaks. Completion does not reset the human-input allowance; a restart resets transient quotas, which is a disclosed bound (tests plus a results note). AC7 No model-visible change in this leaf: no new prompt text, and the history and context are unchanged by scheduling (test). AC8 Narrowing mutants for: streak reset on a non-state-change, a missing cap, stale-ticket admission, a timer not cancelled on invalidation, and the blocker order. Each has a named killer test. Measure and report model requests per scenario.
